The closure trap hiding in an IPC handler

Building an agentic AI IDE from the ground up is no joke. A full day auditing the bridge between the Python daemon, the Electron main process and the React frontend — and the three-line scope bug underneath it all.

Salman Ansari
11 April 2026 · 5 min read

Today was about auditing and bridging the gap between three processes that have to agree with each other: the Python daemon that runs the agents, the Electron main process that brokers everything, and the React frontend the human actually looks at — phases 4, 5 and 6 of the agent system.

The symptom

The frontend wasn't updating provider connectivity statuses. No crash, no error in the console. The UI simply showed nothing, as if no provider existed.

!
The worst bugs in multi-process apps don't throw. One side sends, the other side listens, and something in the middle quietly hands back null.

The cause: a classic JavaScript closure trap

Deep in main.cjs, the settings:get-provider-status IPC handler was trying to close over a lastProviderStatus variable. That variable was declared with let inside a completely different setup function.

Because it wasn't in the enclosing scope, the handler captured undefined and returned null — forever, silently.

main.cjs — the shape of the bug 
// before — each setup function has its own private copy
function setupDaemonHandlers() {
  let lastProviderStatus = null;   // written here…
}

function setupStorageHandlers() {
  ipcMain.handle('settings:get-provider-status', () => {
    return lastProviderStatus;      // …never visible here
  });
}

The fix was to hoist lastProviderStatus to the module level, so the daemon handlers and the secure-storage handlers share one state cache. Instant fix.

✓
When state is read by more than one setup function, it belongs to the module, not to whichever function happened to write it first. A handler registered in one scope cannot see a let declared in another.

Verifying the whole pipeline

With the cache shared, I walked the full event path end to end rather than just confirming the one handler worked:

  • The Python AgentExecutor emits step-by-step events as it works.
  • It streams stdout from shell commands as they run, instead of buffering until the end.
  • Those events travel through the Electron relay into the React StepFeed component.

That path is what makes an agent legible. If the feed lies, the human can't supervise anything.

Security, confirmed not assumed

  • API keys are encrypted through the OS keychain — DPAPI on Windows — not left sitting in app storage.
  • Shell access for the agent is gated behind a strict allowlist, so the agent can run things without being able to run anything.

Where the agent system stands

Out of a 21-point agent system checklist, 19 tasks are fully implemented and verified. The agent can now:

  • securely read files,
  • execute isolated shell commands,
  • and queue code changes into a Monaco DiffEditor for user approval before anything is written to disk.

That last point is the one I care most about. The agent proposes; the diff is the gate; the human decides.
