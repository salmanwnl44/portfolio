Designing Yavin Architect: The Verification Harness That Keeps AI Agents From Drifting

Autonomous code agents don't fail by throwing exceptions. They fail silently: subtly altering system models, inventing facts, hallucinating API signatures, and forgetting constraints. Here is how we engineered Yavin Architect — a rigorous, append-only, contract-driven verification platform that governs every proposal with mathematical determinism.

When software developers talk about autonomous coding agents, the discussion almost always focuses on generation: how fast a model can spit out 200 lines of Python or how clever it is at prompting. But when we started building Yavin, our AI-native code editor, we quickly ran into the harsh reality of real-world software engineering:

!
The Primary Failure Mode: An agent doesn't crash your build. Instead, it subtly edits an architectural boundary, swaps an API parameter, invents an undeclared dependency, and commits a patch that works in isolation while quietly eroding your system architecture.

We realized that to make autonomous code agents viable for mission-critical software, we didn't just need better models. We needed an unyielding, mathematically verifiable referee. We called it Yavin Architect.

This post unpacks the technical architecture of Yavin Architect: the frozen Phase 0 contract system, the single-writer Arbiter pattern, the cryptographic hash-chained append-only ledger, the deterministic checks engine, and how we orchestrated long-running design sessions using Temporal.

1. The Core Invariant: "The Ledger Is Truth"

Most AI backend architectures store state in conventional mutable tables: an agents table, a tasks table, and a models table where rows are updated in place as an agent iterates. This is fatal for AI governance because it destroys provenance. When an agent hallucinates or makes a catastrophic mistake, you cannot prove what state it observed or what caused the drift.

In Yavin Architect, we instituted an iron law codified directly in CLAUDE.md:

PostgreSQL Append-Only Trigger — schema.sql 
CREATE OR REPLACE FUNCTION trg_events_immutable()
RETURNS TRIGGER AS $$
BEGIN
  RAISE EXCEPTION 'events table is strictly append-only; % is forbidden', TG_OP
    USING ERRCODE = '23505';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER events_no_update_or_delete
BEFORE UPDATE OR DELETE OR TRUNCATE ON events
FOR EACH STATEMENT EXECUTE FUNCTION trg_events_immutable();

No code path can ever update, delete, or truncate an event. If a query attempts it, PostgreSQL immediately raises an exception. Every event committed to the ledger is stamped with:

  • A dense sequence number (seq) starting at 0 with no gaps.
  • A cryptographic prev_hash: the canonical SHA-256 hash of the preceding event's wire bytes (sorted keys, compact separators, UTF-8).
  • A verbatim wire timestamp string (ts_wire) stored beside PostgreSQL's native timestamptz, guaranteeing that dumping and replaying the ledger produces identical byte-for-byte hashes across systems.

2. The Arbiter: The Solitary Gatekeeper

If anyone could write to the ledger, chaos would follow. In Yavin Architect, only one module in the entire codebase is permitted to write to the ledger: the Arbiter (src/architect/arbiter.py). We enforce this with an automated architectural test (tests/test_architecture.py) that inspects every module's AST and fails CI if any file other than the Arbiter executes an INSERT on the events table.

01 Per-Project Advisory Locks

Concurrent agent runs or API requests cannot race. The Arbiter serializes commits per project using PostgreSQL advisory transactions: pg_advisory_xact_lock(hashtextextended(project_id, 0)). Parallel commits to separate projects run at full wire speed; commits to the same project wait in an orderly line.

02 Zero-Tolerance Boundary Validation

Before an event is touched, it is deep-validated against Phase 0 frozen JSON schemas (Draft 2020-12). If an embedded claim, patch op, or check result fails schema validation or omits required fields, the Arbiter returns a structured, typed 422 SCHEMA_INVALID with the exact JSON pointer, writing nothing.

03 Mathematical State Projection

The internal tables the Arbiter uses to evaluate rules (arb_claims, arb_model_versions, arb_proposals) are strictly projections. If you drop all arb_* tables, running architect rebuild-state completely reconstructs them by folding the ledger from sequence 0. Dropping cached state never loses information.

04 Typed Rejection Codes

Nothing in the Arbiter fails with a generic error message. Every refusal is mapped to a strict typed rejection code: BASE_MOVED (optimistic concurrency lock violated), PATCH_TARGET_MISSING, DUPLICATE_PROPOSAL, or WAIVER_NOT_HUMAN. Every code is backed by an automated refusal test.

3. The Architecture Engine: How the Pieces Connect

Building a verifiable platform requires clean decoupling. Yavin Architect separates ingestion, gate validation, execution, and semantic memory into distinct layers:

The Model Fold

System models are never written as massive monolithic JSON blobs on every edit. Instead, versions evolve through atomic patch operations (add_element, update_element, remove_element). The Model Fold (model_fold.py) deterministically applies patches to produce a frozen snapshot.

Pure Checks Engine

Checks enforce architectural invariants (e.g. no cyclic dependencies, units compatibility, interface contract compliance). Crucially, checks are pure functions: check(model, ctx, params) -> CheckOutcome. They have zero DB access, zero network calls, and zero randomness.

The Model Gateway

Every LLM interaction routes through architect.gateway. It enforces write-ahead reservation logs (gw_calls) before invoking a provider. If a worker crashes mid-flight, spend is never under-counted. Provider keys are read from env vars and never logged.

Claim-First Knowledge Plane

Knowledge isn't raw chunks of text. It is extracted as structured epistemic claims with provenance, verbatim quotes, conditions, and confidence. Features a dual-backend: Apache AGE graph + pgvector, with a 100% parity pure SQL fallback.

4. Temporal Design Sessions: Surviving the Real World

A typical software architecture task cannot be solved in a single prompt-response loop. An agent must explore documentation, formulate trade-offs, draft proposals, run verification checks, and wait for human review. If your server restarts 45 minutes into an agent's work, what happens?

In standard architectures, everything is lost. In Yavin Architect, design sessions are built on Temporal workflows (src/architect/sessions/workflow.py):

Session State Machine Flow 
PHASE 1: PROBLEM FORMULATION
   │  → Agent audits requirements & linting rules
   ▼
PHASE 2: CONTEXT COMPILATION
   │  → Knowledge retrieval pulls relevant claims & boundary models
   ▼
PHASE 3: EXPLORATION & CANDIDATE SYNTHESIS
   │  → Agent synthesizes model patches & claims
   ▼
PHASE 4: VERIFICATION & CHECKS RUNNER
   │  → Pure checks evaluate structural integrity & cyclic rules
   ▼
PHASE 5: HUMAN GATE DECISION
   │  → APPROVE  │  APPROVE_WITH_RISKS (Signs Waiver)  │  REJECT
   ▼
PHASE 6: ARBITER COMMIT & CONVERGENCE

Because Temporal workflows are fully deterministic, every side effect runs inside an idempotent Activity. Activity IDs, claim IDs, and proposal IDs are mathematically derived from (session_id, phase, round, step), never from uuid4() or system time. If an activity worker dies during an LLM invocation, Temporal heartbeats detect the failure and cleanly retry without generating duplicate ledger entries or orphan reservations.

5. Lessons From Shipping a Rigorous Harness

Building Yavin Architect taught us several foundational truths about building software with AI agents:

  • Contracts must be frozen early: Our Phase 0 JSON schemas were frozen at v1.0 and then v1.2. When a contract caused friction during implementation, our engineers were not allowed to edit the schema — they documented the issue in contracts-PROPOSALS.md and worked around it. This discipline kept our ground truth inviolable.
  • Models should propose, never decide: In our ingestion and extraction pipeline, LLMs extract candidate claims and cite exact verbatim quotes. The pipeline itself determines taint, calculates provenance, verifies the quote exists in the segment, and computes confidence. Never give an LLM write access to your primary domain tables.
  • Waivers are human-only: When an architectural check fails (e.g. a performance budget or interface invariant), an AI agent is forbidden from signing a waiver. It can only flag the finding as an open risk. Only a human engineer through the gate UI can approve with risks, permanently recording their identity on the ledger.
