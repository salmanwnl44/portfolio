Running untrusted tests without handing over the machine

An AI editor that can run your test suite needs a hard boundary around what that suite is allowed to touch. This is the sandbox I built for Yavin — what it blocks, and why time limits and cancellation turned out to be the hard part.

Salman Ansari
Nov 2026 · 6 min read

The problem with a test button

Yavin is a code editor where the AI suggests changes and you review them side by side before anything is accepted. Early on I added a test panel: find your tests, run them, stop them, inspect the results, all without leaving the editor.

That button is more dangerous than it looks. A test file is just code, and code that runs on your machine with your permissions can do anything you can do. The moment an AI is proposing edits to that code, "just shell out and run it" stops being acceptable.

✕
Don't hand the test command straight to a shell. Whatever the suite does — read an SSH key, post to an endpoint, delete a directory one level up — happens silently and with your full privileges.

Drawing the boundary

The execution engine lives in Rust, behind Tauri, and everything the editor wants to run goes through it. It enforces two rules.

  • Unsafe commands are blocked. The runner accepts a known set of test commands, not arbitrary shell input.
  • File access stays inside the project. Paths are resolved and checked against the project root, so a suite can't reach a sibling directory or your home folder.

The second rule needs care, because the obvious implementation is wrong. Checking whether a path string starts with the project root is defeated by ../ segments and by symlinks pointing outward. The check has to happen on the canonical path, after resolution:

sandbox.rs 
// Resolve first, compare second — a prefix check on the raw
// string is defeated by ../ and by symlinks.
fn within_project(root: &Path, candidate: &Path) -> bool {
    let root = match root.canonicalize() { Ok(p) => p, Err(_) => return false };
    let target = match candidate.canonicalize() { Ok(p) => p, Err(_) => return false };
    target.starts_with(&root)
}
!
Canonicalising fails on paths that don't exist yet, so a suite writing a new fixture file looks like a violation. Resolve the parent directory instead, then join the final segment.

The part I underestimated

Blocking things was the easy half. Making runs dependable took longer, and it's what the tests in the repo mostly cover.

Three failure modes matter, and none of them are exotic:

  • A suite that never finishes. An await that never resolves, a test waiting on a port nobody opened. Without a time limit the panel hangs forever and the only way out is killing the editor.
  • A stop button that doesn't stop. Killing the process you spawned isn't enough — test runners spawn children of their own, and those keep going, keep holding ports, keep writing output into a run that's supposedly over.
  • A runner that crashes mid-run. The UI has to end up in a defined state, showing a failure, not a spinner that never resolves.

So every run carries a deadline, cancellation tears down the whole process tree rather than one PID, and a crash is reported as a result like any other. The editor only ever sees one of three outcomes:

test panel 
$ run --suite unit
  ✓ 58 passed            finished
  ⏱ timed out after 30s  cancelled
  ✕ runner crashed       reported
✓
Write the cancellation tests before the happy-path ones. "Does it run the suite" passes almost immediately; "does stop actually stop everything" is the behaviour that quietly regresses.

What I'd tell myself at the start

The sandbox isn't the interesting part of an AI code editor, and that's exactly why it needs to be boring and well covered. The engine has 58 automated tests behind it, and the majority are about time limits, cancellation and crash handling rather than about running tests successfully.

A review screen that shows you every AI change is only trustworthy if accepting one can't quietly run something you didn't read.
