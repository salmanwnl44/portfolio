Building a multi-agent backend from scratch

Two sessions designing and implementing the core infrastructure for Yavin's agent system — hierarchy, guardrails, hooks, persistence and a debug panel to watch it all run.

Salman Ansari
18 April 2026 · 9 min read

This is the production-grade layer underneath the agents: what they're allowed to do, what stops them, and what happens when two of them want the same file.

Agent architecture

  • A 3-tier hierarchy: a Planner (T1) delegating to specialist agents (T2) — Coding, Debug, Refactor, Memory and Git.
  • Agents use intelligent search/replace diffs instead of full-file rewrites. The LLM outputs {"edits": [...]} JSON with exact string patches, applied atomically.
  • The workspace file tree is injected into every agent's system prompt, so agents never create duplicate files for something that already exists.
✓
Search/replace patches beat full-file rewrites on every axis that matters: fewer tokens, a reviewable diff, no silent truncation of the parts the model didn't think about, and atomic application.

The guardrails layer

Five components, each answering a specific way autonomous agents go wrong:

01 AgentLockSystem

A file-level mutex preventing concurrent writes to the same path. Two agents working in parallel is a feature; two agents writing the same file is data loss.

02 TimeoutManager

Auto-releases all locks on timeout and publishes events. A stuck agent must not be able to hold a file hostage forever.

03 RetryExecutor

Exponential backoff, emitting RETRY_TRIGGERED and RETRY_EXHAUSTED events so retries are observable rather than invisible.

04 PermissionGuard

Blocks dangerous shell patterns and path traversal attacks before they execute.

05 CapabilityTier

READ_ONLY / WRITE / PROACTIVE per-agent tool allowlists, with hard-blocked tools. A Debug agent doesn't need write access to earn its keep.

The hook pipeline

Six hook points wrap the entire lifecycle: BEFORE_TOOL_CALL, AFTER_TOOL_CALL, TOOL_RESULT_PERSIST, BEFORE_LLM_CALL, AFTER_LLM_CALL and AGENT_END.

Critically, any hook can veto a tool call before it hits disk. That single property is what makes the whole thing governable — policy lives in one place instead of being re-implemented inside every agent.

The same pipeline routes IDE events: file save → lint + test, error → debug agent, git commit → memory agent.

Infrastructure

  • RunQueue — a per-session asyncio.Lock plus a global Semaphore(10) to serialise agent runs and prevent a thundering herd.
  • SessionStore — aiosqlite-backed persistence for sessions, messages and runs, with indexed queries.
  • ContextEngine — a token-budget-aware sliding window with a compaction strategy, so long sessions degrade gracefully instead of falling off a cliff.
  • StandingOrders — parses AGENTS.md at the workspace root into autonomous / requires-approval / forbidden rules.

That last one is my favourite piece of the design: the rules for what agents may do unattended live in the repository, in version control, reviewable like any other file.

In-process MCP servers

File, Terminal, Git, Memory and Search all run in-process — no subprocess overhead. Every write operation follows the same path:

write path 
permission check → lock acquire → execute → lock release → hook pipeline

One path, every time. No tool gets its own special case, which is exactly why the guardrails can be trusted.

Watching it run

  • A real-time debug panel over WebSocket: agent status, a live file lock map, a log feed (info / warning / error / decision) and an event trace.
  • Ctrl+Shift+D toggles it — it connects only when open and stops reconnecting when closed.
  • File context in chat: type @ for a fuzzy file picker across the workspace; tagged files are injected as context blocks into every agent call, with chips showing what's attached and letting you remove them before sending.

The actual hard part

No single feature here was the difficulty. It was making the pieces composable without coupling:

  • agents talk to MCP,
  • MCP owns the locks,
  • hooks intercept everything,
  • and the LLM never sees raw file paths it has to guess at.

Each layer knows its own job and nothing about the others' internals. Get that wrong and every new agent means touching five files.
